TL;DR

  • Know your record of truth and what it gives up under a partition.
  • Retries are certain. Every mutating call takes an idempotency key.
  • Outbox plus dead letters: a half-failed integration leaves a trace and a way back.
  • The database decides the winner of a race, not request order.
  • Fail open on limits and flags. Fail closed on identity, always.

E1 The record of truth and its guarantees

P1 coreNotesPractice

Know the replication, the partition behaviour, and which reads may be stale.

Replicas
In production only; a single instance elsewhere.
Partition
Refuses rather than diverges (CP).
Reads
Secondary-preferred buys availability and loses read-your-writes.
Writes
Retryable writes off, so idempotency is the app's job.

Any read mode except primary may return stale data. MongoDB docs

Check

E2 Key design from access patterns

P2 depthPracticeLessonNotes

In a key-value store, list the questions first, then design the keys. AWS

Partition keySort keyHolds
USER#<id>IMG#<id>One item
USER#<id>JOB#<id>One job
USER#<id>SESSION#<id>#MSG#…A conversation's messages
  • One partition per owner: every pattern is a key lookup, no secondary index.
  • Atomic ADD counters, not read-modify-write.
  • Over-fetch, then delete only the head of what you read.

E6 Concurrency: races and atomic updates

Check, then act

Read the count, compare, then write. Both requests pass.

Increment and read

Optimistic

E7 Failure handling: fail open or fail closed

P2 depthNotesPracticeLesson

Time out every call, retry at one layer, and choose open or closed per control.

243×load on a failing database: 3 retries at each of 5 layers

Back off exponentially, add jitter, cap it. Builders' Library

Fail open

  • Rate limiters
  • Feature flags
  • Daily caps backstop abuse

Fail closed

  • Authentication
  • Authorisation
  • Tenancy
  • A tool call when the link is down
Exercise
List every control in one service and mark each open or closed.
Check
Name one control that must never fail open, and why.

CAP

Caching

E10 Time, ordering and clocks

P2 depthNotesLesson

Store timezone-aware UTC. Order with keys, not with hope.

  • Local time across a daylight-saving change gives a doubled or missing hour.
  • Per-key ordering in a topic, or sessions in a queue.
  • Daily caps that roll at UTC midnight are easy to reason about.
